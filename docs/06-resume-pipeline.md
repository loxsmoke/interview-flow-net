# 06 — Resume Pipeline

The tightly-coupled trio — **tagging heuristic** (`_tag_resume_heuristic`), **tagged preview** (`taggedToHtml`, spec'd in 04 §4.6), and **styled .docx export** (`_build_resume_doc_styled`, spec'd in 02 §2.6) — must be ported together and tested against the original's fixture corpus (`tests/app/Parse-Test-Resume.docx` → `tests/app/parsed-resume.txt`).

Source: `app/main.py` (parsing/tagging ~lines 2242–2617).

## 6.1 File intake

Accepted `.pdf .docx .doc .txt .md .rtf`; max 10 MB; magic bytes checked (`%PDF` for PDF, `PK\x03\x04` for DOCX). Output: `{ text, raw, tagged, filename, chars }` where `text` = clean markdown, `raw` = diagnostic dump, `tagged` = auto-tagged DSL.

## 6.2 PDF → markdown (original: PyMuPDF; port candidate: PdfPig)

Font-size heuristic against the **modal body size** of the document:

- span size ≥ 1.5 × body → `# `
- ≥ 1.3 × → `## `
- ≥ 1.15 × → `### `
- Bullet characters `•●◦▪▸▶‣⁃∙` → `- `
- Bold runs → `**…**`, italic → `*…*`, bold-italic → `***…***`

> **Implemented** with PdfPig (`PdfExtractor`). The thresholds, bullet handling and emission rules are ported exactly, but PdfPig groups words rather than PyMuPDF spans, so line/span segmentation on complex layouts can differ. This is the one place in the pipeline without byte-parity proof — DOCX (the format the fixture corpus uses) *is* byte-identical. Tolerance accepted; revisit if a real PDF resume extracts poorly.

## 6.3 DOCX → two representations (original: python-docx; port candidate: Open XML SDK)

1. **Clean markdown** (`_extract_markdown_from_docx`) — used as `resume`. Sample of expected output (from `tests/app/parsed-resume.txt`):

   ```
   # John Smith
   john.smith@gmail.com | Mountain View, CA | www.linkedin.com/in/john-smith

   **Technical Skills**
   **Languages:** C, C++, D, E--

   ***Software Engineer*** **| Bigtech	1/2020 – 2/2021**
   Made impact.
   ▪ Increase increment by 100%
   ```

2. **Diagnostic raw dump** (`_extract_text_from_docx`) — shown in the Raw tab, format per paragraph:

   ```
   (Style, indent=1.3cm, align=left, before=6pt, numPr(...), tabs=[...]) (bold, size=11pt)text
   ```

   Reproduce the same annotation vocabulary (style name, indent in cm, alignment, spacing-before in pt, numbering, tab stops; run-level bold/size).

## 6.4 Tagging heuristic (`_tag_resume_heuristic`)

Converts the clean markdown into the tag DSL (02 §2.4). Driven by:

- **Section-heading map** (`section-headings.md`, hot-reloaded each parse — 02 §2.5) classifying headings into `summary | experience | skills | additional`.
- ALL-CAPS lines (≤ 65 chars) always count as section headings.
- Within a section, lines are tagged `[Summary] / [Job title] / [Job summary] / [Job bullet] / [Skill] / [Additional info]` by section type and line shape.

> **Implemented** (`ResumeTagger`) and verified **byte-identical** against output generated by the original's own `_tag_resume_heuristic` on the fixture resume.
